# Frostrail Mod 包规范 v2

2026-10-30

一个 Mod 就是一个 ZIP：把文件按要放的位置摆好，拖进管理器即可；mod.json、设置描述和更新链接都可选。规范只规定文件放哪，不规定 Mod 怎么写，也不要求使用前置。

## 包的样子与部署规则

大多数 Lua Mod 只需要压缩自己的文件夹；要放到别处的文件才按游戏根目录摆。

```text
FrostrailQuickstash-0.3.0.zip         普通 Lua Mod：只压缩自己的文件夹
├─ mod.json                            可选
├─ README.md                           可选
└─ FrostrailQuickstash/
   ├─ Scripts/main.lua
   ├─ module.lua …
   ├─ defaults.json                    可选：配置默认值
   └─ settings.json                    可选：设置表单

FrostrailAssist-0.3.0.zip             带资源：PAK 直接放包根
├─ mod.json
├─ FrostrailAssist/…
└─ FrostrailAssist_P.pak / .utoc / .ucas

UE4SS-FrostrailCore-0.3.0.zip         要放到其他位置：按游戏根目录摆
├─ mod.json
└─ Frostrail/Binaries/Win64/…
```

管理器按顺序判断包根的每一项，每项只走一条规则：

1. 包根只有一个文件夹，且它不符合第 4、5 条 → 先进入这一层再判断（兼容多套了一层的压缩包）。
2. `.pak`、`.utoc`、`.ucas` 文件 → `Frostrail/Content/Paks/~mods/`。
3. 其他文件（mod.json、README、LICENSE、图片等）→ 留在管理器里，不进游戏目录。
4. 与游戏根下一级目录同名的文件夹（如 `Frostrail`）→ 按游戏根原样放。
5. 含 `Scripts/main.lua` 或 `dlls/main.dll` 的文件夹 → UE4SS Mod，放到 `Frostrail/Binaries/Win64/ue4ss/Mods/<文件夹名>/`，并自动加入 UE4SS 的加载列表。
6. 其余文件夹 → 报错并指出是哪一项，不猜。

- 同一个文件已属于另一个已装 Mod 时，安装失败并列出冲突文件，不自动覆盖。
- 游戏目录里原有、但不属于任何 Mod 的文件（例如手动装的 UE4SS）会先备份，停用或卸载时还原；列在 `keep_existing` 里的则保留玩家原有的那份。
- 同一个 id 再装一次就是更新：开关、加载顺序和 config.json 都保留，旧版有而新版没有的文件会被移除。

## mod.json（可选）

不写 mod.json 也能装；写了就能显示名称和简介、声明前置、接入在线更新。每个字段都可以单独省略。

| 字段 | 说明 | 不写时 |
| --- | --- | --- |
| `id` | 稳定身份，用于更新和前置；改显示名不改 id | 唯一的 UE4SS 文件夹名 → 唯一 PAK 的文件名 → ZIP 文件名 |
| `name` | 显示名，字符串或 `{"zh": "…", "en": "…"}` | 同 id |
| `version` | 任意版本文字；与已装版本不同即提示可更新（允许回退） | 显示“—” |
| `author` | 作者 | 不显示 |
| `description` | 简介，显示在详情页；写法同 name | 取 README 第一段 |
| `requires` | 前置包的 id 数组 | 无前置 |
| `update` | 一个 GitHub 链接，见“在线更新” | 不检查更新 |
| `notices` | `enable` / `disable` / `uninstall` 三种操作前展示的提示，写法同 name | 不提示 |
| `keep_existing` | 游戏目录里已有时不覆盖、不接管的文件（游戏根相对路径） | 无 |
| `data_paths` | Mod 运行时在自己文件夹以外写的文件或目录（游戏根相对路径），卸载时一并删除 | 无 |

示例（堆叠）：

```json
{
  "id": "FrostrailStacks",
  "name": {"zh": "堆叠", "en": "Stacks"},
  "version": "0.3.0",
  "author": "Yuuka",
  "description": {"zh": "可堆叠物品的上限默认 ×10，可按类别调整，单位重量不变。", "en": "Multiplies stack limits by 10 by default with per-category overrides."},
  "requires": ["FrostrailCore"],
  "update": "https://github.com/<owner>/<repo>",
  "notices": {
    "disable": {"zh": "关闭前请在启用状态下把超量堆叠拆回原上限并保存。", "en": "Split oversized stacks and save before disabling."},
    "uninstall": {"zh": "卸载前请在启用状态下把超量堆叠拆回原上限并保存。", "en": "Split oversized stacks and save before uninstalling."}
  }
}
```

`<owner>/<repo>` 是占位，发布仓库后再填。

## 设置：defaults.json 与 settings.json（可选）

两个文件都放在 Mod 文件夹里，与 config.json 同级。defaults.json 写全部配置项的默认值，是默认值的唯一来源；settings.json 只说明哪些键要显示在管理器和 F8 里、怎么显示，不重复默认值和类型。

```json
[
  {"key": "range_m", "label": {"zh": "快存距离（米）", "en": "Quick stash range (m)"}, "min": 1, "max": 100, "live": true},
  {"key": "colors.items", "label": {"zh": "物品颜色", "en": "Item color"}, "type": "color", "live": true, "group": {"zh": "高亮", "en": "Highlights"}},
  {"key": "recipes", "label": {"zh": "种植配方", "en": "Recipes"}, "columns": [{"key": "item", "label": {"zh": "物品", "en": "Item"}}, {"key": "output", "label": {"zh": "产出", "en": "Output"}, "min": 1, "integer": true}]}
]
```

| 属性 | 用途 |
| --- | --- |
| `key` | 配置键；点号表示嵌套，如 `colors.items` |
| `label` | 显示名，字符串或 `{"zh", "en"}` |
| `live` | `true` 表示也出现在游戏内 F8、改完立即生效（Mod 需在 `changed()` 里应用）；不写则下次启动生效 |
| `group` | 可选的分组标题 |
| `help` | 可选的一行说明 |
| `type` | 只在默认值看不出来时写：`color`（六位十六进制，如 `50D890`） |
| `options` | 选择项：值的数组，或 `[{"value": …, "label": …}]` |
| `min` / `max` / `integer` / `step` | 数字限制 |
| `columns` | 对象数组的表格列；每列可写 `key`、`label` 和上面的数字限制 |
| `value_type` | 对象（名称/值表）的默认值为空时，值的类型，如 `number` |

控件按 defaults.json 里的值推断：布尔 → 勾选框；数字 → 数字框；字符串 → 文本框；对象数组 → 表格；其他数组 → 列表；对象 → 名称/值表。

- 不在 settings.json 里的键不显示，适合存内部状态（如格子锁位置）。
- config.json 由 Mod 首次运行时生成；之后每次启动，支持库会补齐缺少的顶层键。
- 管理器只写被改动的键，其他键和未知键原样保留；游戏运行时管理器里的设置只读。

## 在线更新（可选）

`update` 填一个 GitHub 链接，有两种写法；版本文字与已装版本不同即提示可更新（允许回退）。

| 链接 | 管理器怎么找新版本 |
| --- | --- |
| 仓库首页 `https://github.com/<owner>/<repo>` | 读仓库最近的 Release，找文件名以 `<id>-<版本>.zip` 结尾的附件（前面可以有前缀，如 `UE4SS-FrostrailCore-0.3.0.zip`），取最新的一个；找不到时，若最新 Release 只有一个 ZIP，就用它，并以标签（去掉开头的 v）作版本 |
| 目录 `https://github.com/<owner>/<repo>/tree/<分支>/<目录>` | 读该目录里 mod.json 的 version；这个目录本身就是一个包（mod.json 加要部署的文件夹），下载时取同一次提交 |

- 一个仓库放多个 Mod 时，把各包按 `<id>-<版本>.zip` 命名放进同一个 Release 即可，每个包各自判断版本。
- 目录写法会下载整个仓库快照，仓库里有大文件时用 Release 写法。
- 玩家也可以把同样的链接粘贴进管理器直接安装；没写 `update` 的包，会记住安装时用的链接作为更新来源。
- 不需要 GitHub 账号；请求过多被限流时，管理器会提示稍后再试或拖入本地包。

## 可选：Lua 支持库（UE4SS-FrostrailCore）

只有想用配置读写、F8 即时设置、原生改键或角色生命周期回调的 Lua Mod 才需要它，需要时在 `requires` 里写 `FrostrailCore`。支持库只做这些事，不负责加载、启停、排序或兼容；游戏以后有官方接口时，Mod 只需换掉这几处调用。

最小入口 `Scripts/main.lua`：

```lua
local C = require("Frostrail.runtime").create()   -- id 默认取 Mod 文件夹名
local M = {}

function M:setup()   -- 在这里声明原生按键，玩家在游戏“设置 → 控制”里改键
    C.action("Hello", "打个招呼", "J", function() C.message("Hello") end)
end

function M:changed() -- F8 改了 live 设置后调用，此时 M.cfg 已是新值
end

return C.start(M)
```

- `create()` 的参数均可省略；`dir` 从调用文件位置推出，`id` 默认取 Mod 文件夹名。
- `M.cfg`：读取 config.json，再补 defaults.json 中缺少的顶层键；两个文件都没有时是空表。
- 生命周期回调都可省略：`setup`、`init`、`player_ready(pc, pawn)`、`player_left`、`changed`。
- 有自身目录的 settings.json 就自动登记到 F8，不用写代码；登记时携带 config 路径和 defaults。F8 只显示 `live` 字段，保存后通知对应 Mod 重读。
- 其他工具函数（`C.log`、`C.retain`、`C.hook` 等）可用可不用，见支持库源码。
- 不用这套库也完全可以：普通 UE4SS Lua 或 C++ Mod 照常按上面的规则打包安装。

## 卸载会删什么

卸载的目标是彻底移除这个 Mod，玩家可以选择只保留设置。

- 删除：本包部署的文件、它在自己 UE4SS 文件夹里运行时生成的文件、`data_paths`、mods.txt 条目、`packages/<id>.zip` 和 `originals/<id>/`。勾选“保留设置”时留下 config.json。
- 保留：还原回去的原文件、`keep_existing` 的文件，以及 state.json 里属于其他包的文件。
- 清理完成后删除空目录；仍有保留文件的目录留下。
- 存档里的游戏状态不在卸载范围内；需要玩家先在游戏里处理的事，请写进 `notices`。
